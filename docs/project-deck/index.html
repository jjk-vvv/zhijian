1.4 技术栈与「为什么是它」

层选型在讲解里要说的一句话
视图Vue 3 + <script setup>组合式 API 让「状态 + 行为」按业务聚在一起，而不是散在 data/methods 里。
构建Vite开发态按需编译，改一个组件只重编一个模块，热更新快。

数据PostgreSQL 18关系模型天然适合书架、关注、书友会这类多对多关系；统计用 SQL 聚合最直接。
认证JWT（Bearer）前后端分离 + 小程序共用一套鉴权：签 token、带 token、验 token。

02

Vue 前端：从入口到一次交互的完整链路

这一节是主体。按「入口 → 路由 → 布局 → 状态 → 请求 → 组件 → 样式」的顺序讲，正好对应一次页面访问的真实执行顺序。

2.1 入口只有三行

// src/main.js
import { createApp } from 'vue'
import App from './App.vue'
import router from './router/index.js'
import './styles.css'
import './styles-app.css'

createApp(App).use(router).mount('#app')

讲解要点：Vue 3 没有「全局 Vue 实例」，createApp 返回一个应用实例，插件（这里是 router） 通过 .use() 装配，最后挂到 #app。两套 CSS 的引入顺序就是层叠顺序：先基础样式，再应用样式。

2.2 路由：一张表决定「能去哪、要不要登录」

路由表把 16 个页面分成三类：公开页（发现、详情、书单、动态、书友会、他人主页）、 需要登录（书架、手记、划线、统计、目标、设置）、游客页（登录、注册）。 区分方式不是写在组件里，而是写在 meta.requiresAuth。 

const router = createRouter({
  history: createWebHashHistory(),   // 静态部署也能刷新
  routes: [
    { path: '/', name: 'discover', component: DiscoverView },
    { path: '/book/:slug', name: 'book-detail', component: () => import('../views/BookDetailView.vue') },
    { path: '/shelf', name: 'shelf', component: () => import('../views/ShelfView.vue'), meta: { requiresAuth: true } },
    // … notes / highlights / stats / goals / settings 同理
    { path: '/:pathMatch(.*)*', name: 'not-found', component: () => import('../views/NotFoundView.vue') },
  ],
  scrollBehavior(to, from, savedPosition) {
    if (savedPosition) return savedPosition
    // 等旧页面淡出后再回顶，避免切换时「先跳一下」
    return new Promise((resolve) => setTimeout(() => resolve({ top: 0 }), 160))
  },
})

三个细节值得展开讲：

  • 首屏同步、其余异步。只有发现页是静态 import，其余全部 () => import()，Vite 会切成独立 chunk。
  • 守卫里做鉴权。beforeEach 先 await ensureReady()（用已有 token 换用户），再判断 to.meta.requiresAuth，未登录就带上 redirect 回登录页。
  • 已登录不再进登录页。访问 /login 且已有用户时直接回首页。
router.beforeEach(async (to) => {
  const user = await ensureReady()
  if (to.meta.requiresAuth && !user) {
    return { path: '/login', query: { redirect: to.fullPath } }
  }
  if ((to.name === 'login' || to.name === 'register') && user) {
    return { path: '/' }
  }
  return true
})

router.afterEach((to) => {
  document.title = `${to.meta.title} · 纸间`
})
为什么要 await？刷新页面时内存里没有用户，但 localStorage 里可能有 token。守卫必须等「用 token 换用户」这一步完成，否则会把已登录用户误判成游客踢回登录页。

2.3 App.vue：全局布局 + 转场 + 预取

根组件只做四件事：放页头页脚、给路由出口加过渡、空闲时预取其余页面、管理焦点。

<template>
  <a class="skip-link" href="#main-content">跳到主要内容</a>
  <AppHeader />
  <main id="main-content" ref="main" tabindex="-1">
    <RouterView v-slot="{ Component }">
      <Transition :name="transitionName" mode="out-in">
        <component :is="Component" :key="pageKey" />
      </Transition>
    </RouterView>
  </main>
  <AppFooter />
  <ToastNotice :message="toast" :tone="tone" />
</template>

转场方向由路由层级决定：进入子页面横向左滑，返回上级横向右滑，同级只做淡入淡出。这就是「page-forward / page-back / page-fade」三个类名的来源。

watch(
  () => route.path,
  async (path, previous) => {
    if (previous && path.startsWith(`${previous}/`)) transitionName.value = 'page-forward'
    else if (previous && previous.startsWith(`${path}/`)) transitionName.value = 'page-back'
    else transitionName.value = 'page-fade'
    await nextTick()
    if (!document.querySelector('[aria-modal="true"]')) main.value?.focus({ preventScroll: true })
  },
)

预取则利用了浏览器空闲时间：等首屏渲染完、网络空闲后，把所有异步路由的工厂函数跑一遍，组件 chunk 就进了缓存，之后点哪里都不再等加载。

function prefetchRoutes() {
  router.getRoutes().forEach((record) => {
    const component = record.components?.default
    if (typeof component === 'function') component().catch(() => {})
  })
}

// onMounted 里：
if ('requestIdleCallback' in window) {
  window.requestIdleCallback(prefetchRoutes, { timeout: 2500 })
} else {
  setTimeout(prefetchRoutes, 1200)
}

2.4 响应式：ref、computed、watch 各管什么

API在本项目里的典型用法讲解落点
refshelf、notes、搜索关键词、当前分类基本类型与数组/对象都可用；模板里自动解包。
reactiveuseAuth 里的 { user, ready, loading }一组相关状态放一个对象，适合「会话」这种整体。
computedfilteredBooks、stats、isSaved派生数据不重复存，依赖变了才重算。
watch路由变化切转场、当前用户变化刷新书架处理「变化之后要做副作用」，而不是算值。
readonlycomposable 对外只暴露只读状态状态只能通过方法改，避免组件里到处直接赋值。

以书架统计为例，四个数字全部是算出来的，没有第四个 ref：

const stats = computed(() => ({
  total: shelf.value.length,
  wishlist: shelf.value.filter((b) => b.status === 'wishlist').length,
  reading: shelf.value.filter((b) => b.status === 'reading').length,
  finished: shelf.value.filter((b) => b.status === 'finished').length,
  notes: notes.value.length,
}))

2.5 组合式函数：把「业务」装进模块级单例

这是整个前端最值得讲的设计。useAuth、useLibrary、useToast 都不是每次调用新建状态， 而是模块级只创建一次，所有组件共享同一份。这样页头显示的用户名、书架页的书、详情页的「已收藏」按钮，天然同步。 

// useLibrary.js —— 状态定义在模块作用域，只执行一次
const shelf = ref([])
const notes = ref([])
const loading = ref(false)

export function useLibrary() {
  return {
    shelf: readonly(shelf),
    notes: readonly(notes),
    stats,
    refreshAll,
    addBook,
    setStatus,
    updateProgress,
    saveNote,
    deleteNote,
    isSaved,
  }
}

乐观更新 + 防抖是另一个讲解点。拖动阅读进度条时先改本地值，450ms 内的连续拖动只发一次请求；失败则回滚并提示。

function updateProgress(slug, value) {
  const entry = shelf.value.find((item) => item.slug === slug)
  if (!entry) return
  const progress = Math.min(100, Math.max(0, Number(value) || 0))
  const wasFinished = entry.progress >= 100
  entry.progress = progress
  entry.status = deriveStatus(progress)
  clearTimeout(progressTimers.get(slug))
  progressTimers.set(slug, setTimeout(async () => {
    try {
      const result = await api.shelf.update(slug, { progress })
      Object.assign(entry, result)
      if (result.progress >= 100 && !wasFinished) notify('又读完一本，值得纪念')
    } catch (error) {
      notify(error.message, 'error')
    }
  }, 450))
}

refreshAll 用 Promise.all 并行拉书架和手记，登录态变化时统一刷新：

async function refreshAll() {
  await ensureReady()
  if (!currentUser.value) {
    shelf.value = []; notes.value = []
    shelfLoaded.value = true; notesLoaded.value = true
    return
  }
  loading.value = true
  try {
    await Promise.all([refreshShelf(), refreshNotes()])
  } catch {
    notify('书架加载失败，请稍后重试', 'error')
  } finally {
    loading.value = false
  }
}

2.6 请求层：一个函数兜住所有接口

api/client.js 做了五件事：拼 URL、带 token、解析 JSON、把失败统一成 ApiError、 遇到 401 清 token 并广播事件。api 对象则是按业务分组的「接口字典」，页面只关心方法名。 

export async function request(path, { method = 'GET', body, query } = {}) {
  const headers = {}
  const token = getToken()
  if (token) headers.Authorization = `Bearer ${token}`
  if (body !== undefined) headers['Content-Type'] = 'application/json'

  let response
  try {
    response = await fetch(buildUrl(path, query), {
      method, headers,
      body: body !== undefined ? JSON.stringify(body) : undefined,
    })
  } catch {
    throw new ApiError(0, 'NETWORK_ERROR', '无法连接服务器，请确认后端服务已启动')
  }

  if (response.status === 204) return null
  const payload = await response.json().catch(() => null)
  if (!response.ok) {
    const error = payload?.error || {}
    if (response.status === 401 && token) {
      setToken('')
      window.dispatchEvent(new CustomEvent('zhijian:unauthorized'))
    }
    throw new ApiError(response.status, error.code || 'REQUEST_FAILED',
      error.message || '请求失败，请稍后再试', error.details)
  }
  return payload
}

useAuth 监听这个事件：任何请求 401，全局用户状态立即清空，路由守卫下次跳转就会把用户送回登录页。 一套机制，所有页面受益。 

if (typeof window !== 'undefined') {
  window.addEventListener('zhijian:unauthorized', () => {
    state.user = null
    state.ready = true
  })
}

2.7 组件通信：props 向下，emit 向上，v-model 做双向

以发现页的筛选工具条为例：分类和排序是父页面的状态，子组件只负责展示与派发。

<CategoryTabs v-model="category" />
<SearchToolbar v-model="search" v-model:sort="sort" />
<BookGrid :books="filteredBooks" :is-saved="isSaved"
          @detail="selectedBook = $event" @save="addBook" />

v-model 的本质是 :modelValue + @update:modelValue； v-model:sort 则把名字换成 sort，一个组件同时承载两个双向绑定。 书卡组件内部只发事件，不直接调 API——「数据怎么改」永远留在组合式函数里。 

<!-- BookCard.vue -->
<button class="book-detail-trigger" @click="emit('detail', book)">
  <BookCover :book="book" />
</button>
<button class="save-button" :class="{ saved }" :disabled="saved"
        @click="emit('save', book.id)">…</button>

插槽用于「结构固定、内容可变」的容器，例如区块标题右侧的计数：

<SectionHeading title="总有一本，与你此刻有关" description="…">
  <text class="collection-count">{{ filteredBooks.length }} 本精选</text>
</SectionHeading>

2.8 列表、条件、表单：三个最常用的模板能力

  • 列表：v-for 必须配稳定的 key（书籍用 slug，手记用 id），否则删除/排序时 DOM 复用会错位。
  • 条件：v-if 控制「有没有」，v-show 控制「显不显示」。弹层用 v-if，因为要销毁内部状态。
  • 表单：登录/注册/写手记都是 v-model + @submit.prevent，提交时按钮进入 loading，失败把 ApiError.message 显示在表单顶部。

2.9 过渡动画：为什么用 mode="out-in"

默认过渡会新旧两个页面同时存在，导致高度叠加、滚动位置跳动。改成 mode="out-in" 后，旧页面先退场再进新页面， 配合 scrollBehavior 的 160ms 延时，视觉上就是「一页翻过去」而不是「抖一下」。 

/* 三个方向共用一个时长，保证节奏一致 */
.page-fade-enter-active,.page-fade-leave-active,
.page-forward-enter-active,.page-forward-leave-active,
.page-back-enter-active,.page-back-leave-active{ transition: opacity .22s ease, transform .22s ease }
.page-forward-enter-from{ opacity:0; transform: translateX(18px) }
.page-back-enter-from{ opacity:0; transform: translateX(-18px) }

03

迁移到 uni-app：换的是外壳，不是思路

这一节回答一个问题：同一套 Vue 代码，怎么变成能跑在微信开发者工具里的小程序。

3.1 先说结论

迁移保留了 100% 的 Vue 语法与组件拆分，替换的是四样东西：
页面注册（router → pages.json）、导航（router.push → uni.switchTab）、标签（div/img → view/image）、平台能力（localStorage → uni.setStorageSync）。

uniapp/ 是一个独立的 HBuilderX 工程，不依赖 npm：HBuilderX 自带 uni-app 编译器， 打开目录就能运行到浏览器、微信开发者工具或手机基座。

3.7 平台 API：存储与导航各自封一层

// utils/storage.js —— 把 uni 的同步存储包成和 localStorage 一样的用法
export const getItem = (key, fallback = null) => {
  try {
    const value = uni.getStorageSync(key)
    return value === '' || value === undefined ? fallback : value
  } catch { return fallback }
}
export const setItem = (key, value) => {
  try { uni.setStorageSync(key, value) } catch {}
}

这样 useLibrary 这类业务代码几乎不用改：Web 版用 localStorage，小程序版 import 这个文件即可。 「平台差异只出现在 utils 层」是这次迁移最重要的工程约束。

4.4 分层：routes 很薄，service 才做业务

以书籍模块为例，路由只做三件事：取参数、调 service、返回 JSON。所有 SQL 和业务判断都在 service 里。

// modules/books/routes.js
router.get('/categories', asyncHandler(async (_req, res) => {
  res.json(await service.listCategories())
}))

router.get('/', optionalAuth, asyncHandler(async (req, res) => {
  res.json(await service.listBooks(req.query))
}))

router.get('/:slug', optionalAuth, asyncHandler(async (req, res) => {
  res.json(await service.getBookDetail(req.params.slug, req.user?.id))
}))

asyncHandler 是关键小工具：它把 async 函数包一层，捕获到的异常交给 next(err)， 这样就不用每个路由写 try/catch，错误会统一落到 errorHandler。

讲解口径：路由层 = 协议适配（HTTP 进、JSON 出）；服务层 = 业务与数据；数据层 = 连接与事务。
任何一层都不越界，代码就能一直讲得清。

4.5 JWT：签发、解析、可选与必须

export function signToken(user) {
  return jwt.sign({ sub: user.id, handle: user.handle }, env.jwtSecret, {
    expiresIn: env.jwtExpiresIn,
  })
}

async function resolveUser(token) {
  let payload
  try {
    payload = jwt.verify(token, env.jwtSecret)
  } catch {
    throw unauthorized('登录状态已失效，请重新登录')
  }
  const { rows } = await query(
    `select id, email, handle, display_name, bio, avatar_color, location, website, is_private, created_at
       from users where id = $1`, [payload.sub])
  if (!rows[0]) throw unauthorized('账号不存在')
  return rows[0]
}

两个中间件的差别，是讲鉴权时最值得强调的一句：

中间件没有 tokentoken 无效用在哪
optionalAuth放行，req.user 为空记为 req.authError，仍放行发现页、书籍详情（登录后多返回「是否已收藏」）
requireAuth401401书架、手记、统计等 /me 接口

4.6 统一响应与错误

// 成功：直接返回业务对象
{ "items": [...], "total": 52 }

// 失败：永远是同一个形状
{ "error": { "code": "RATE_LIMITED", "message": "操作太频繁，请稍后再试" } }

前端 ApiError 就是照着这个形状解析的，所以任何接口报错，页面都能拿到一句人话和稳定的错误码。 限流、鉴权、校验、数据库异常，最终都收敛到同一处。

4.7 数据库连接池与事务

export const pool = new Pool({
  connectionString: env.databaseUrl,
  max: 10,
  idleTimeoutMillis: 30_000,
})

export const query = (text, params) => pool.query(text, params)

export async function withTransaction(handler) {
  const client = await pool.connect()
  try {
    await client.query('begin')
    const result = await handler(client)
    await client.query('commit')
    return result
  } catch (error) {
    await client.query('rollback')
    throw error
  } finally {
    client.release()
  }
}

「什么时候需要事务」可以举一个具体例子：把书加入书单时，要同时插入 list_items 并更新 lists.updated_at； 两步必须同生共死，否则书单列表的时间会与内容不一致。

4.8 统计聚合：把计算交给 SQL

阅读统计页的四个数字（总时长、连续天数、读完本数、平均评分）不是前端算的，而是后端用聚合查询一次返回： sum(duration)、按日期分组算连续、按状态计数、avg(rating)。 热力图则按「年 + 周 + 星期」聚合，前端只负责上色。 

GET /api/v1/me/stats/overview      → 总览卡片
GET /api/v1/me/stats/heatmap?year  → 全年每一天的阅读量
GET /api/v1/me/stats/annual?year   → 年度回顾
GET /api/v1/me/stats/friends-weekly → 好友本周阅读对比
讲解落点：「统计」是最能体现前后端分工的模块——聚合放数据库，展示放前端，中间只传结果，不传原始记录。

4.9 安全清单

  • 密码用 bcrypt 哈希存储，接口永不返回密码字段。
  • JWT 密钥来自环境变量，不写进仓库；token 有过期时间。
  • 所有 SQL 使用参数化查询（$1），不拼字符串。
  • 列表接口统一分页，避免一次拉全表。
  • 写操作校验资源归属：只能改自己的书架、手记、书单。
  • 限流 + 请求体大小限制，挡住最基础的刷接口与超大包。

07

十个高频追问

回答时先说结论，再补一句原因，最后指一个文件。不要让答案停在概念上。

为什么用 Hash 路由而不是 History 路由？

因为要能直接丢到任意静态空间。History 路由刷新 /shelf 需要服务端 rewrite 到 index.html，Hash 不需要。代价是 URL 里多一个 #，对这个项目可以接受。

为什么状态不放进 Pinia？

这个项目的共享状态只有「会话、书架、手记、Toast」四块，模块级 ref 加 readonly 导出已经够用，少一层依赖。等状态跨模块耦合变多，再迁 Pinia 是平滑的。

乐观更新会不会导致数据不一致？

会，所以每个乐观更新都保留 previous，请求失败时 Object.assign(entry, previous) 回滚并提示。进度条还有 450ms 防抖，减少无效请求。

守卫里为什么要 await ensureReady()？

刷新页面时内存没有用户，只有 localStorage 里的 token。不等「token 换用户」完成就判断，会把已登录用户误判成游客。ensureReady 内部用 readyPromise 去重，多次调用只发一次请求。

401 之后前端怎么处理？

request() 清 token 并派发 zhijian:unauthorized，useAuth 监听后清空用户；下一次路由跳转守卫就会把用户送回登录页，并带上 redirect。

小程序为什么没有做动态路由？

小程序页面必须预先在 pages.json 注册，没有 /book/:slug 这种运行时路径。书籍详情改为组件弹层，既不占页面栈，返回行为也更自然。

uni-app 里 H5 和微信小程序的导航差在哪？

小程序有原生 tabBar，必须用 switchTab；H5 没有，用 redirectTo。差异被收进 utils/nav.js 的条件编译里，页面只调 goTab()。

为什么统计不在前端算？

原始记录可能有上千条，前端算要全量拉取。SQL 聚合只返回结果（几个数字、一年的每日计数），传输和计算都更省，也避免前端逻辑与后端口径不一致。

JWT 存在 localStorage 安全吗？

有 XSS 风险，所以这里做了三件事：不用 v-html 渲染用户内容、Helmet 安全头、token 有过期时间。更严格的做法是 HttpOnly Cookie + CSRF token，但会牺牲小程序的通用性。

这套代码怎么继续扩展？

后端加一个 modules/xxx/{routes,service}.js 并在 app.js 挂载；前端加一个 view、一条路由、一组 api 方法。uni-app 侧如果该页面需要上小程序，再补一条 pages.json 与标签替换。三处改动都是加法，不动老代码。
